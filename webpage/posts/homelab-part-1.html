Homelab Part 1: Base Setup, Installing Proxmox, and Getting Backups Running

The boring part. No Kubernetes, no dashboards, just hypervisors and backups.

Most homelab posts jump straight to the fun stuff. This one doesn't. It's about installing Proxmox, setting it up properly and making sure there are backups before anything else happens. If you came for Kubernetes, see you in a later part.

The hardware

The cluster started on two Dell Precision 3561 workstation laptops:

  • pve-01: 192.168.1.100
  • pve-02: 192.168.1.101

Laptops as servers sounds like a bad idea. It isn't. The battery is a free UPS, they use little power, they're silent and they fit on a shelf. For a two-node cluster that's mostly for learning, that's all I need.

Installing Proxmox VE

The install itself is easy: put the Proxmox VE ISO on a USB stick, boot, click through the installer. The choices that actually matter happen during the install and right after it.

1. Filesystem. I kept the default, ext4 on LVM-thin. ZFS is tempting, but it wants RAM, and on a laptop I'd rather give that RAM to VMs. Thin provisioning lets me hand out more disk space to VMs than I really have, without reserving it up front.

2. Static IPs from day one. Both nodes got fixed addresses (.100 and .101) in the installer. A hypervisor that changes its IP is a hypervisor you have to go looking for. Set it once, write it down, leave it alone.

3. Hostnames. pve-01 and pve-02. Short, numbered, boring. Clever names are fun for about six months.

Setup after the install

A fresh Proxmox needs a few things before it's really usable.

Repositories. Out of the box, Proxmox uses the enterprise repo, which fails without a subscription. Switch to the no-subscription repo:

# Disable enterprise repo, enable no-subscription
sed -i "s/^deb/#deb/" /etc/apt/sources.list.d/pve-enterprise.list
echo "deb http://download.proxmox.com/debian/pve bookworm pve-no-subscription" \
  > /etc/apt/sources.list.d/pve-no-subscription.list
apt update && apt full-upgrade -y

Updates first. Do a full upgrade and reboot before you create a single VM. Otherwise you end up moving VMs around later just to patch the host, and that's annoying for no reason.

Creating the cluster. Once both nodes are installed and updated, it's two commands: pvecm create on the first node, pvecm add on the second. After that, one web UI manages both machines.

The quorum problem. Two nodes have a built-in flaw. If one dies, the other one doesn't have a majority and refuses to do cluster operations. The fix is a QDevice, a third vote that doesn't have to be a full Proxmox node. Mine is a Raspberry Pi 3 running corosync-qnetd. Its whole job is to vote. That's enough to keep the cluster working when a node is down.

# On the cluster, after setting up the Pi:
pvecm qdevice setup <pi-ip>

Backups: Proxmox Backup Server

A homelab without backups is just a slow way to lose data. Before I deployed anything I'd miss, I set up Proxmox Backup Server (PBS) as a VM (VMID 110) on the cluster itself.

Yes, running the backup server on the thing it backs up is a compromise. What matters is that the datastore lives on separate storage, not on the cluster's own disks. If a node dies, the backups are still there, and PBS itself is reinstalled in twenty minutes.

Why PBS and not plain vzdump backups into a folder?

  • Deduplication. Dozens of snapshots take only a fraction of the space, because unchanged chunks are stored once.
  • Incremental backups. After the first full backup, only changed blocks are sent. Nightly backups finish in minutes.
  • Verification jobs. PBS checks stored chunks against their checksums regularly, so I find corruption before I need a restore.
  • Pruning. keep-last, keep-daily, keep-weekly: set once, enforced automatically.

Connecting it is simple. Add PBS as storage in the Proxmox datacenter, create a backup job for all VMs, schedule it for every night. Done.

My rule: a workload doesn't exist until the backup job covers it. New VM or new container, it goes into the backup schedule the same day.

Where this leaves things

After step one I have:

  • Two Proxmox nodes, patched, with static IPs, in a cluster
  • A QDevice keeping quorum honest
  • PBS running nightly deduplicated backups with verification

No services, no containers, nothing to show off. But everything that comes later sits on this, and it's backed up from the first day.

That's the point of step one. Get the boring layer right, so you never have to think about it again.

Homelab Teil 1: Grundsetup, Proxmox-Installation und laufende Backups

Der langweilige Teil. Kein Kubernetes, keine Dashboards, nur Hypervisoren und Backups.

Die meisten Homelab-Beiträge springen direkt zu den spannenden Sachen. Dieser nicht. Hier geht es darum, Proxmox zu installieren, sauber einzurichten und Backups zu haben, bevor irgendetwas anderes passiert. Wenn du wegen Kubernetes hier bist: bis in einem späteren Teil.

Die Hardware

Der Cluster hat auf zwei Dell Precision 3561 Workstation-Laptops angefangen:

  • pve-01: 192.168.1.100
  • pve-02: 192.168.1.101

Laptops als Server klingt nach einer schlechten Idee. Ist es aber nicht. Der Akku ist eine Gratis-USV, sie brauchen wenig Strom, sind leise und passen ins Regal. Für einen Zwei-Node-Cluster, der vor allem zum Lernen da ist, reicht das völlig.

Proxmox VE installieren

Die Installation selbst ist einfach: Proxmox-VE-ISO auf einen USB-Stick, booten, durch den Installer klicken. Die Entscheidungen, die wirklich zählen, kommen während der Installation und direkt danach.

1. Dateisystem. Ich habe den Standard gelassen, ext4 auf LVM-thin. ZFS ist verlockend, will aber RAM, und auf einem Laptop gebe ich den lieber den VMs. Mit Thin Provisioning kann ich den VMs mehr Speicher zuteilen, als ich eigentlich habe, ohne ihn vorher zu reservieren.

2. Statische IPs ab Tag eins. Beide Nodes haben im Installer feste Adressen bekommen (.100 und .101). Ein Hypervisor, der seine IP wechselt, ist ein Hypervisor, den du suchen musst. Einmal setzen, aufschreiben, nicht mehr anfassen.

3. Hostnamen. pve-01 und pve-02. Kurz, nummeriert, langweilig. Kreative Namen machen etwa sechs Monate lang Spass.

Einrichtung nach der Installation

Ein frisches Proxmox braucht ein paar Dinge, bevor es wirklich brauchbar ist.

Repositories. Ab Werk nutzt Proxmox das Enterprise-Repo, und das schlägt ohne Subscription fehl. Also aufs No-Subscription-Repo wechseln:

# Enterprise-Repo deaktivieren, No-Subscription aktivieren
sed -i "s/^deb/#deb/" /etc/apt/sources.list.d/pve-enterprise.list
echo "deb http://download.proxmox.com/debian/pve bookworm pve-no-subscription" \
  > /etc/apt/sources.list.d/pve-no-subscription.list
apt update && apt full-upgrade -y

Zuerst Updates. Mach ein komplettes Upgrade und starte neu, bevor du auch nur eine VM erstellst. Sonst schiebst du später VMs herum, nur um den Host zu patchen, und das nervt ohne Grund.

Cluster erstellen. Wenn beide Nodes installiert und aktuell sind, sind es zwei Befehle: pvecm create auf dem ersten Node, pvecm add auf dem zweiten. Danach verwaltet eine Web-UI beide Maschinen.

Das Quorum-Problem. Zwei Nodes haben einen eingebauten Fehler. Fällt einer aus, hat der andere keine Mehrheit und verweigert Cluster-Operationen. Die Lösung ist ein QDevice, eine dritte Stimme, die kein vollständiger Proxmox-Node sein muss. Bei mir ist das ein Raspberry Pi 3 mit corosync-qnetd. Sein einziger Job ist abstimmen. Das reicht, damit der Cluster weiterläuft, wenn ein Node weg ist.

# Auf dem Cluster, nachdem der Pi eingerichtet ist:
pvecm qdevice setup <pi-ip>

Backups: Proxmox Backup Server

Ein Homelab ohne Backups ist einfach eine langsame Art, Daten zu verlieren. Bevor ich irgendetwas deployt habe, das ich vermissen würde, habe ich den Proxmox Backup Server (PBS) als VM (VMID 110) auf dem Cluster selbst aufgesetzt.

Ja, den Backup-Server auf dem Ding laufen zu lassen, das er sichert, ist ein Kompromiss. Wichtig ist, dass der Datastore auf separatem Speicher liegt und nicht auf den Disks des Clusters. Stirbt ein Node, sind die Backups noch da, und PBS selbst ist in zwanzig Minuten neu installiert.

Warum PBS und nicht einfach vzdump-Backups in einen Ordner?

  • Deduplizierung. Dutzende Snapshots brauchen nur einen Bruchteil des Platzes, weil unveränderte Chunks nur einmal gespeichert werden.
  • Inkrementelle Backups. Nach dem ersten Voll-Backup werden nur geänderte Blöcke übertragen. Die nächtlichen Backups sind in Minuten fertig.
  • Verifikationsjobs. PBS prüft die gespeicherten Chunks regelmässig gegen ihre Prüfsummen. So finde ich Fehler, bevor ich ein Restore brauche.
  • Pruning. keep-last, keep-daily, keep-weekly: einmal eingestellt, läuft automatisch.

Das Anbinden ist einfach. PBS als Storage im Proxmox-Datacenter hinzufügen, einen Backup-Job für alle VMs anlegen, jede Nacht laufen lassen. Fertig.

Meine Regel: Ein Workload existiert erst, wenn der Backup-Job ihn abdeckt. Neue VM oder neuer Container, kommt am selben Tag in den Backup-Plan.

Was am Ende steht

Nach Schritt eins habe ich:

  • Zwei Proxmox-Nodes, gepatcht, mit statischen IPs, im Cluster
  • Ein QDevice, das das Quorum ehrlich hält
  • PBS mit nächtlichen, deduplizierten Backups und Verifikation

Keine Dienste, keine Container, nichts zum Angeben. Aber alles, was später kommt, baut darauf auf und ist ab dem ersten Tag gesichert.

Darum geht es bei Schritt eins. Die langweilige Schicht richtig machen, damit du nie wieder darüber nachdenken musst.

Homelab część 1: Konfiguracja bazowa, instalacja Proxmoxa i działające backupy

Nudna część. Bez Kubernetesa, bez dashboardów, tylko hipernadzorcy i backupy.

Większość wpisów o homelabie od razu skacze do fajnych rzeczy. Ten nie. Chodzi tu o to, żeby zainstalować Proxmoxa, porządnie go skonfigurować i mieć backupy, zanim wydarzy się cokolwiek innego. Jeśli przyszedłeś po Kubernetesa, widzimy się w którejś z kolejnych części.

Sprzęt

Klaster zaczął się od dwóch laptopów workstation Dell Precision 3561:

  • pve-01: 192.168.1.100
  • pve-02: 192.168.1.101

Laptopy jako serwery brzmią jak zły pomysł. Ale nie są. Bateria to darmowy UPS, mało prądu, cisza i mieszczą się na półce. Do dwuwęzłowego klastra, który służy głównie do nauki, w zupełności wystarczy.

Instalacja Proxmox VE

Sama instalacja jest prosta: ISO Proxmox VE na pendrive, boot, przeklikać instalator. Decyzje, które naprawdę mają znaczenie, zapadają w trakcie instalacji i zaraz po niej.

1. System plików. Zostawiłem domyślny ext4 na LVM-thin. ZFS kusi, ale chce RAM-u, a na laptopie wolę go oddać VM-kom. Thin provisioning pozwala przydzielić VM-kom więcej miejsca, niż faktycznie mam, bez rezerwowania go z góry.

2. Statyczne IP od pierwszego dnia. Oba węzły dostały stałe adresy (.100 i .101) już w instalatorze. Hipernadzorca, który zmienia IP, to hipernadzorca, którego trzeba szukać. Ustaw raz, zapisz, nie ruszaj.

3. Nazwy hostów. pve-01 i pve-02. Krótko, z numerem, nudno. Pomysłowe nazwy bawią mniej więcej pół roku.

Konfiguracja po instalacji

Świeży Proxmox potrzebuje kilku rzeczy, zanim będzie naprawdę używalny.

Repozytoria. Domyślnie Proxmox korzysta z repozytorium enterprise, które bez subskrypcji nie działa. Trzeba przełączyć na no-subscription:

# Wyłącz repo enterprise, włącz no-subscription
sed -i "s/^deb/#deb/" /etc/apt/sources.list.d/pve-enterprise.list
echo "deb http://download.proxmox.com/debian/pve bookworm pve-no-subscription" \
  > /etc/apt/sources.list.d/pve-no-subscription.list
apt update && apt full-upgrade -y

Najpierw aktualizacje. Pełny upgrade i restart, zanim powstanie choć jedna VM. Inaczej później przenosisz VM-ki tylko po to, żeby załatać hosta, a to irytuje bez powodu.

Tworzenie klastra. Gdy oba węzły są zainstalowane i aktualne, to dwa polecenia: pvecm create na pierwszym węźle, pvecm add na drugim. Potem jeden panel webowy zarządza obiema maszynami.

Problem kworum. Dwa węzły mają wbudowaną wadę. Gdy jeden padnie, drugi nie ma większości i odmawia operacji klastrowych. Rozwiązanie to QDevice, trzeci głos, który nie musi być pełnym węzłem Proxmoxa. U mnie to Raspberry Pi 3 z corosync-qnetd. Jego jedyne zadanie to głosować. To wystarcza, żeby klaster działał, gdy węzła nie ma.

# Na klastrze, po skonfigurowaniu Pi:
pvecm qdevice setup <pi-ip>

Backupy: Proxmox Backup Server

Homelab bez backupów to po prostu powolny sposób na utratę danych. Zanim wdrożyłem cokolwiek, czego byłoby mi szkoda, postawiłem Proxmox Backup Server (PBS) jako VM (VMID 110) na samym klastrze.

Tak, trzymanie serwera backupów na tym, co on backupuje, to kompromis. Ważne jest to, że datastore leży na osobnym storage, a nie na dyskach klastra. Gdy węzeł padnie, backupy zostają, a sam PBS reinstaluję w dwadzieścia minut.

Dlaczego PBS, a nie zwykłe backupy vzdump do folderu?

  • Deduplikacja. Dziesiątki snapshotów zajmują ułamek miejsca, bo niezmienione fragmenty są zapisywane raz.
  • Backupy przyrostowe. Po pierwszym pełnym backupie wysyłane są tylko zmienione bloki. Nocne backupy kończą się w kilka minut.
  • Weryfikacja. PBS regularnie sprawdza zapisane fragmenty z sumami kontrolnymi, więc błędy znajduję, zanim będę potrzebował restore.
  • Retencja. keep-last, keep-daily, keep-weekly: ustawione raz, działa samo.

Podpięcie jest proste. Dodaj PBS jako storage w datacenter Proxmoxa, utwórz zadanie backupu dla wszystkich VM-ek, ustaw na każdą noc. Gotowe.

Moja zasada: workload nie istnieje, dopóki nie obejmuje go backup. Nowa VM albo nowy kontener trafia do harmonogramu tego samego dnia.

Co mam po kroku pierwszym

Po kroku pierwszym mam:

  • Dwa węzły Proxmoxa, załatane, ze statycznymi IP, w klastrze
  • QDevice, które pilnuje uczciwego kworum
  • PBS z nocnymi, deduplikowanymi backupami i weryfikacją

Żadnych usług, żadnych kontenerów, nic do pochwalenia się. Ale wszystko, co przyjdzie później, stoi na tym i jest backupowane od pierwszego dnia.

O to chodzi w kroku pierwszym. Zrobić nudną warstwę dobrze, żeby nigdy więcej nie trzeba było o niej myśleć.
