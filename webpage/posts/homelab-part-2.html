Homelab Part 2: The Raspberry Pi Tiebreaker and a Thunderbolt Cluster Link

A €30 Pi that keeps my cluster honest, and a fast link between two laptops without buying a switch.

Update, November 2026: This post describes the first version of the lab. The Pi is retired: a third laptop (pve-03) joined the cluster, so three nodes vote now. I also measured the Thunderbolt link properly: 14.8 Gbit/s in practice. 40 Gbit/s is only what the port is rated for. The current setup is on the homelab page.

In Part 1 I installed Proxmox on two Dell Precision 3561 nodes and got backups running. Two things only got a sentence there, so they get a whole post now: the Raspberry Pi 3 QDevice and the two networks. That's 1Gb Ethernet to the LAN, plus a direct 40Gbps Thunderbolt 4 cable between the nodes.

Part A: The Raspberry Pi that does almost nothing

Why two nodes are a problem

Proxmox clustering runs on Corosync, and Corosync decides things by majority vote. Every node has one vote, and the cluster only works when more than half of the votes are there. That's quorum.

With two nodes:

  • Both nodes up: 2 of 2 votes, quorum. Fine.
  • One node down: 1 of 2 votes, no majority, quorum lost.

So the moment one node fails, which is exactly what a cluster is supposed to handle, the node that's still alive locks itself. No starting VMs, no config changes. It's protecting itself from split-brain, which is the correct behaviour. It's also no help at all at 2 AM.

The QDevice

You don't need a third full Proxmox node to fix this. Corosync supports an external QDevice: a small daemon (corosync-qnetd) on any Linux machine that gives the cluster a third vote without being part of it. It runs no VMs, stores no data and does nothing except break ties.

That's a perfect job for the Raspberry Pi 3 that was sitting in my drawer:

  • It uses about 2-3 watts
  • It's completely passive. All it does is answer "who gets quorum?"
  • If the Pi dies while both nodes are fine, nothing happens (2 of 3 votes is still a majority)

Setup

On the Pi (Raspberry Pi OS / Debian):

apt install corosync-qnetd

On the Proxmox nodes:

apt install corosync-qdevice   # on both nodes
pvecm qdevice setup <pi-ip>    # once, from either node

Check it:

pvecm status
# Expected: 3 total votes, "Qdevice" listed, quorum 2

Now any single failure, node A, node B or the Pi, still leaves 2 of 3 votes, and the cluster keeps working. Extra cost: one Pi and a power supply.

One tip: give the Pi a static IP and treat it like infrastructure, not like a toy. A QDevice that changes its address over DHCP is worse than no QDevice, because you'll spend an hour debugging weird quorum issues before you think of checking the Pi.

Part B: Two networks, two jobs

The nodes have two completely separate network paths. The idea is simple: cluster traffic and user traffic should never fight over the same cable.

Link 1: 1Gb Ethernet, the front door

Both nodes are on the LAN over normal gigabit Ethernet (192.168.1.100 and .101). This carries:

  • Web UI and SSH
  • VM traffic to the rest of the network and the internet
  • Backup traffic to storage
  • Corosync heartbeats

1GbE is plenty for that. Management is a few kilobytes, and thanks to incremental PBS backups even the backup jobs rarely fill the line.

Link 2: Thunderbolt 4, the fast backbone

This is the part that makes a laptop cluster actually good. Both Precision 3561s have Thunderbolt 4 ports, and Thunderbolt can do IP networking over a direct cable. Connect the two nodes with one TB4 cable and Linux shows it as a network interface through the thunderbolt-net kernel module.

That's a point-to-point link rated at 40Gbps for the price of a cable. No 10/25/40GbE cards, no switch, no SFP+ modules. That hardware would cost more than the laptops.

The interface shows up (as thunderbolt0 or something like en0, depending on the setup) and you configure it like any other NIC, just on its own private subnet:

pve-01: 10.0.0.1/30  (thunderbolt)
pve-02: 10.0.0.2/30  (thunderbolt)

A /30 is enough. Two hosts, point to point, nothing else will ever live there.

What goes over Thunderbolt

Everything heavy that happens between the nodes:

  • Live migration. Moving a running VM means copying all of its RAM to the other node. Over 1GbE, a VM with 8GB of RAM takes more than a minute. Over TB4 it's seconds. Migration goes from "let's plan this" to "just do it".
  • Big transfers between nodes, like moving disks, templates or restore data.

In the Proxmox datacenter options you set the migration network to the Thunderbolt subnet, and Proxmox sends all migration traffic there:

Datacenter → Options → Migration Settings → Network: 10.0.0.0/30

What doesn't go over Thunderbolt (on purpose)

Corosync stays on Ethernet. That sounds wrong at first. Why not put cluster traffic on the fastest link? Because Corosync doesn't care about bandwidth. It cares about latency and reliability, and it needs a network that both nodes and the QDevice can reach. The Pi doesn't have a Thunderbolt port. So heartbeats, quorum votes and the QDevice all stay on the 1GbE LAN, where all three of them are.

The split:

TrafficLinkWhy
Management, VM traffic, backups1GbEReaches everything, fast enough
Corosync + QDevice1GbEThe Pi has to be reachable; latency matters, not bandwidth
Live migration, big node-to-node copiesTB4 (14.8 Gbit/s measured)RAM-sized transfers, kept away from everything else

Things to know

  • You won't actually get 40Gbps. thunderbolt-net costs CPU, so real numbers are well below that. I measured 14.8 Gbit/s. Still several times faster than any Ethernet gear I could afford.
  • It's more fragile than Ethernet. Replugging the cable or suspend/resume can drop the link. A systemd unit or udev rule that sets the interface up again on hotplug saves you some headaches.
  • Two nodes only. Thunderbolt networking is point to point. This only works because the cluster is a pair. A third node needs a different answer.

The whole picture

Three boxes, two networks:

  • Two Proxmox nodes with a private Thunderbolt link for the heavy stuff
  • Both nodes plus a Raspberry Pi on the 1GbE LAN, where quorum lives
  • Any one of the three can die and the cluster doesn't care

The Pi and the TB4 cable together cost less than a nice dinner. That's what I like about homelabs: enterprise ideas on pocket-money hardware.

Homelab Teil 2: Der Raspberry Pi als Zünglein an der Waage und ein Thunderbolt-Clusterlink

Ein 30-€-Pi, der meinen Cluster ehrlich hält, und ein schneller Link zwischen zwei Laptops, ganz ohne Switch.

Update, November 2026: Dieser Beitrag beschreibt die erste Version des Labs. Der Pi ist in Rente: Ein dritter Laptop (pve-03) ist dem Cluster beigetreten, jetzt stimmen drei Nodes ab. Ausserdem habe ich den Thunderbolt-Link richtig gemessen: 14,8 Gbit/s in der Praxis. 40 Gbit/s ist nur die Nennrate des Ports. Den aktuellen Stand gibt es auf der Homelab-Seite.

In Teil 1 habe ich Proxmox auf zwei Dell Precision 3561 installiert und die Backups zum Laufen gebracht. Zwei Dinge haben dort nur einen Satz bekommen, deshalb jetzt ein ganzer Beitrag: das Raspberry Pi 3 QDevice und die zwei Netzwerke. Also 1-Gb-Ethernet ins LAN plus ein direktes 40-Gbps-Thunderbolt-4-Kabel zwischen den Nodes.

Teil A: Der Raspberry Pi, der fast nichts tut

Warum zwei Nodes ein Problem sind

Proxmox-Clustering läuft auf Corosync, und Corosync entscheidet per Mehrheit. Jeder Node hat eine Stimme, und der Cluster funktioniert nur, wenn mehr als die Hälfte der Stimmen da ist. Das ist das Quorum.

Mit zwei Nodes:

  • Beide Nodes laufen: 2 von 2 Stimmen, Quorum. Alles gut.
  • Ein Node ist weg: 1 von 2 Stimmen, keine Mehrheit, Quorum verloren.

Genau in dem Moment, in dem ein Node ausfällt, also genau dann, wofür ein Cluster da ist, sperrt sich der überlebende Node selbst. Keine VMs starten, keine Konfiguration ändern. Er schützt sich vor Split-Brain, und das ist korrekt. Um 2 Uhr nachts hilft es dir trotzdem kein bisschen.

Das QDevice

Dafür brauchst du keinen dritten vollen Proxmox-Node. Corosync unterstützt ein externes QDevice: einen kleinen Daemon (corosync-qnetd) auf irgendeiner Linux-Kiste, der dem Cluster eine dritte Stimme gibt, ohne dazuzugehören. Er betreibt keine VMs, speichert keine Daten und macht nichts ausser Gleichstände aufzulösen.

Perfekter Job für den Raspberry Pi 3, der bei mir in der Schublade lag:

  • Braucht etwa 2-3 Watt
  • Komplett passiv. Er beantwortet nur die Frage „wer bekommt das Quorum?"
  • Stirbt der Pi, während beide Nodes laufen, passiert nichts (2 von 3 Stimmen sind immer noch eine Mehrheit)

Einrichtung

Auf dem Pi (Raspberry Pi OS / Debian):

apt install corosync-qnetd

Auf den Proxmox-Nodes:

apt install corosync-qdevice   # auf beiden Nodes
pvecm qdevice setup <pi-ip>    # einmal, von einem der Nodes

Prüfen:

pvecm status
# Erwartet: 3 Stimmen gesamt, "Qdevice" gelistet, Quorum 2

Jetzt bleiben bei jedem einzelnen Ausfall, Node A, Node B oder der Pi, 2 von 3 Stimmen übrig, und der Cluster läuft weiter. Zusatzkosten: ein Pi und ein Netzteil.

Ein Tipp: Gib dem Pi eine statische IP und behandle ihn wie Infrastruktur, nicht wie ein Spielzeug. Ein QDevice, das per DHCP seine Adresse wechselt, ist schlimmer als gar keins. Du suchst dann eine Stunde lang komische Quorum-Fehler, bevor du auf die Idee kommst, den Pi zu prüfen.

Teil B: Zwei Netzwerke, zwei Aufgaben

Die Nodes haben zwei komplett getrennte Netzwerkpfade. Die Idee ist simpel: Cluster-Traffic und normaler Traffic sollen sich nie um dasselbe Kabel streiten.

Link 1: 1-Gb-Ethernet, die Eingangstür

Beide Nodes hängen über normales Gigabit-Ethernet im LAN (192.168.1.100 und .101). Darüber laufen:

  • Web-UI und SSH
  • VM-Traffic ins restliche Netz und ins Internet
  • Backup-Traffic zum Storage
  • Corosync-Heartbeats

Dafür reicht 1GbE locker. Verwaltung sind ein paar Kilobytes, und dank inkrementeller PBS-Backups füllen selbst die Backup-Jobs die Leitung selten.

Link 2: Thunderbolt 4, das schnelle Rückgrat

Das ist der Teil, der einen Laptop-Cluster richtig gut macht. Beide Precision 3561 haben Thunderbolt-4-Ports, und Thunderbolt kann IP-Netzwerk über ein direktes Kabel. Verbinde die zwei Nodes mit einem TB4-Kabel, und Linux zeigt es über das Kernelmodul thunderbolt-net als Netzwerkschnittstelle an.

Das ist ein Punkt-zu-Punkt-Link mit 40 Gbps Nennrate zum Preis eines Kabels. Keine 10/25/40GbE-Karten, kein Switch, keine SFP+-Module. Die Hardware würde mehr kosten als die Laptops.

Die Schnittstelle taucht auf (als thunderbolt0 oder so ähnlich wie en0, je nach Setup) und wird wie jede andere NIC konfiguriert, nur in einem eigenen privaten Subnetz:

pve-01: 10.0.0.1/30  (thunderbolt)
pve-02: 10.0.0.2/30  (thunderbolt)

Ein /30 reicht. Zwei Hosts, Punkt zu Punkt, da wird nie etwas anderes wohnen.

Was über Thunderbolt läuft

Alles Schwere, was zwischen den Nodes passiert:

  • Live-Migration. Eine laufende VM zu verschieben heisst, ihren ganzen RAM auf den anderen Node zu kopieren. Über 1GbE braucht eine VM mit 8 GB RAM über eine Minute. Über TB4 sind es Sekunden. Migration wird von „das planen wir mal" zu „mach einfach".
  • Grosse Transfers zwischen Nodes, zum Beispiel Disks, Templates oder Restore-Daten.

In den Datacenter-Optionen von Proxmox stellst du das Migrationsnetz auf das Thunderbolt-Subnetz, und Proxmox schickt den ganzen Migrationsverkehr dorthin:

Datacenter → Options → Migration Settings → Network: 10.0.0.0/30

Was absichtlich nicht über Thunderbolt läuft

Corosync bleibt auf Ethernet. Klingt erst mal falsch. Warum nicht den Cluster-Traffic auf den schnellsten Link legen? Weil Corosync Bandbreite egal ist. Wichtig sind Latenz und Zuverlässigkeit, und es braucht ein Netz, das beide Nodes und das QDevice erreichen. Der Pi hat keinen Thunderbolt-Port. Also bleiben Heartbeats, Quorum-Stimmen und das QDevice im 1GbE-LAN, wo alle drei sind.

Die Aufteilung:

TrafficLinkWarum
Verwaltung, VM-Traffic, Backups1GbEErreicht alles, schnell genug
Corosync + QDevice1GbEDer Pi muss erreichbar sein; Latenz zählt, nicht Bandbreite
Live-Migration, grosse Kopien zwischen NodesTB4 (14,8 Gbit/s gemessen)Transfers in RAM-Grösse, getrennt von allem anderen

Gut zu wissen

  • 40 Gbps bekommst du in echt nicht. thunderbolt-net kostet CPU, die echten Werte liegen deutlich darunter. Gemessen habe ich 14,8 Gbit/s. Trotzdem ein Mehrfaches von allem, was ich mir an Ethernet-Hardware leisten könnte.
  • Empfindlicher als Ethernet. Kabel neu einstecken oder Suspend/Resume kann den Link trennen. Eine systemd-Unit oder udev-Regel, die die Schnittstelle bei Hotplug wieder einrichtet, spart Nerven.
  • Nur zwei Nodes. Thunderbolt-Netzwerk ist Punkt zu Punkt. Das klappt nur, weil der Cluster ein Paar ist. Ein dritter Node braucht eine andere Lösung.

Das Gesamtbild

Drei Kisten, zwei Netzwerke:

  • Zwei Proxmox-Nodes mit einem privaten Thunderbolt-Link für die schweren Sachen
  • Beide Nodes plus ein Raspberry Pi im 1GbE-LAN, wo das Quorum wohnt
  • Jede der drei Kisten darf ausfallen, und dem Cluster ist es egal

Pi und TB4-Kabel kosten zusammen weniger als ein gutes Abendessen. Genau das mag ich an Homelabs: Enterprise-Ideen auf Taschengeld-Hardware.

Homelab część 2: Raspberry Pi jako rozjemca i łącze klastrowe Thunderbolt

Pi za 30 €, które pilnuje uczciwości klastra, i szybkie łącze między dwoma laptopami bez kupowania switcha.

Aktualizacja, listopad 2026: Ten wpis opisuje pierwszą wersję labu. Pi jest na emeryturze: trzeci laptop (pve-03) dołączył do klastra, więc teraz głosują trzy węzły. Zmierzyłem też porządnie łącze Thunderbolt: 14,8 Gbit/s w praktyce. 40 Gbit/s to tylko nominalna przepustowość portu. Aktualna konfiguracja jest na stronie homelabu.

W części 1 zainstalowałem Proxmoxa na dwóch węzłach Dell Precision 3561 i uruchomiłem backupy. Dwie rzeczy dostały tam tylko jedno zdanie, więc teraz dostają cały wpis: QDevice na Raspberry Pi 3 i dwie sieci. Czyli Ethernet 1 Gb do LAN-u plus bezpośredni kabel Thunderbolt 4 40 Gb/s między węzłami.

Część A: Raspberry Pi, które nie robi prawie nic

Dlaczego dwa węzły to problem

Klaster Proxmoxa działa na Corosyncu, a Corosync decyduje większością głosów. Każdy węzeł ma jeden głos i klaster działa tylko wtedy, gdy jest ponad połowa głosów. To jest kworum.

Przy dwóch węzłach:

  • Oba węzły działają: 2 z 2 głosów, kworum. W porządku.
  • Jeden węzeł pada: 1 z 2 głosów, brak większości, kworum stracone.

Czyli w momencie, gdy jeden węzeł padnie, a właśnie po to jest klaster, ten, który przeżył, sam się blokuje. Nie uruchomisz VM-ek, nie zmienisz konfiguracji. Chroni się przed split-brainem i to jest poprawne. O 2 w nocy nic ci to jednak nie pomaga.

QDevice

Nie potrzebujesz do tego trzeciego pełnego węzła Proxmoxa. Corosync obsługuje zewnętrzne QDevice: mały daemon (corosync-qnetd) na dowolnej maszynie z Linuksem, który daje klastrowi trzeci głos, nie będąc jego częścią. Nie uruchamia VM-ek, nie trzyma danych i nie robi nic poza rozstrzyganiem remisów.

Idealna robota dla Raspberry Pi 3, które leżało u mnie w szufladzie:

  • Pobiera około 2-3 watów
  • Jest całkowicie pasywne. Odpowiada tylko na pytanie „kto dostaje kworum?"
  • Jeśli Pi padnie, gdy oba węzły działają, nic się nie dzieje (2 z 3 głosów to nadal większość)

Konfiguracja

Na Pi (Raspberry Pi OS / Debian):

apt install corosync-qnetd

Na węzłach Proxmoxa:

apt install corosync-qdevice   # na obu węzłach
pvecm qdevice setup <pi-ip>    # raz, z dowolnego węzła

Sprawdzenie:

pvecm status
# Oczekiwane: 3 głosy łącznie, "Qdevice" na liście, kworum 2

Teraz przy każdej pojedynczej awarii, węzeł A, węzeł B albo Pi, zostają 2 z 3 głosów i klaster działa dalej. Dodatkowy koszt: jedno Pi i zasilacz.

Jedna rada: daj Pi statyczne IP i traktuj je jak infrastrukturę, a nie zabawkę. QDevice, które zmienia adres przez DHCP, jest gorsze niż brak QDevice. Spędzisz godzinę na szukaniu dziwnych problemów z kworum, zanim pomyślisz o sprawdzeniu Pi.

Część B: Dwie sieci, dwa zadania

Węzły mają dwie całkowicie oddzielne ścieżki sieciowe. Pomysł jest prosty: ruch klastra i zwykły ruch nie powinny walczyć o ten sam kabel.

Łącze 1: Ethernet 1 Gb, drzwi wejściowe

Oba węzły są w LAN-ie przez zwykły gigabitowy Ethernet (192.168.1.100 i .101). Tędy idzie:

  • Panel webowy i SSH
  • Ruch VM-ek do reszty sieci i internetu
  • Ruch backupów do storage
  • Heartbeaty Corosynca

Do tego 1GbE w zupełności wystarcza. Zarządzanie to kilka kilobajtów, a dzięki przyrostowym backupom PBS nawet zadania backupu rzadko zapychają łącze.

Łącze 2: Thunderbolt 4, szybki kręgosłup

To ta część, dzięki której klaster na laptopach jest naprawdę dobry. Oba Precision 3561 mają porty Thunderbolt 4, a Thunderbolt potrafi sieć IP po bezpośrednim kablu. Połącz węzły jednym kablem TB4, a Linux pokaże go jako interfejs sieciowy przez moduł jądra thunderbolt-net.

To łącze punkt-punkt o nominalnej przepustowości 40 Gb/s w cenie kabla. Bez kart 10/25/40GbE, bez switcha, bez modułów SFP+. Taki sprzęt kosztowałby więcej niż laptopy.

Interfejs się pojawia (jako thunderbolt0 albo coś w stylu en0, zależnie od konfiguracji) i konfigurujesz go jak każdą inną kartę, tylko we własnej prywatnej podsieci:

pve-01: 10.0.0.1/30  (thunderbolt)
pve-02: 10.0.0.2/30  (thunderbolt)

/30 wystarczy. Dwa hosty, punkt-punkt, nic innego tam nigdy nie zamieszka.

Co idzie po Thunderbolcie

Wszystko ciężkie, co dzieje się między węzłami:

  • Migracja na żywo. Przeniesienie działającej VM to skopiowanie całego jej RAM-u na drugi węzeł. Po 1GbE VM z 8 GB RAM-u potrzebuje ponad minuty. Po TB4 to sekundy. Migracja zmienia się z „trzeba to zaplanować" w „po prostu zrób".
  • Duże transfery między węzłami, np. dyski, szablony albo dane do restore.

W opcjach datacenter Proxmoxa ustawiasz sieć migracji na podsieć Thunderbolt i Proxmox wysyła tam cały ruch migracji:

Datacenter → Options → Migration Settings → Network: 10.0.0.0/30

Co celowo nie idzie po Thunderbolcie

Corosync zostaje na Ethernecie. Na początku brzmi to źle. Czemu nie dać ruchu klastra na najszybsze łącze? Bo Corosynca nie obchodzi przepustowość. Liczą się opóźnienie i niezawodność, a potrzebuje sieci, do której dotrą oba węzły i QDevice. Pi nie ma portu Thunderbolt. Więc heartbeaty, głosy kworum i QDevice zostają w LAN-ie 1GbE, gdzie są wszystkie trzy.

Podział:

RuchŁączeDlaczego
Zarządzanie, ruch VM, backupy1GbEDociera wszędzie, wystarczająco szybkie
Corosync + QDevice1GbEPi musi być osiągalne; liczy się opóźnienie, nie przepustowość
Migracja na żywo, duże kopie między węzłamiTB4 (14,8 Gbit/s zmierzone)Transfery wielkości RAM-u, oddzielone od reszty

Warto wiedzieć

  • Prawdziwych 40 Gb/s nie zobaczysz. thunderbolt-net zjada CPU, więc realne wyniki są wyraźnie niższe. Zmierzyłem 14,8 Gbit/s. I tak kilka razy szybciej niż jakikolwiek Ethernet, na który byłoby mnie stać.
  • Jest delikatniejszy niż Ethernet. Przepięcie kabla albo suspend/resume potrafi zerwać łącze. Unit systemd albo reguła udev, która ustawia interfejs ponownie przy hotplugu, oszczędza nerwów.
  • Tylko dwa węzły. Sieć Thunderbolt jest punkt-punkt. Działa tylko dlatego, że klaster to para. Trzeci węzeł potrzebuje innego rozwiązania.

Cały obrazek

Trzy pudełka, dwie sieci:

  • Dwa węzły Proxmoxa z prywatnym łączem Thunderbolt do ciężkich rzeczy
  • Oba węzły plus Raspberry Pi w LAN-ie 1GbE, gdzie mieszka kworum
  • Każde z trzech może paść, a klastra to nie obchodzi

Pi i kabel TB4 kosztują razem mniej niż dobra kolacja. To właśnie lubię w homelabach: pomysły z enterprise na sprzęcie za kieszonkowe.
